# AGENTS.md — bb-plugin-provider-pi-durable

Operational guidelines and invariants for `bb-plugin-provider-pi-durable`.

## Hard rules for this repository

⛔ **ALWAYS COMMIT AND PUSH TO MAIN.**
Для этого репозитория (`VanDalkvist/bb-plugin-provider-pi-durable`) ВСЕГДА коммитить и пушить осмысленную работу в ветку `main` без переспроса у Вани. Не оставлять выполненные циклы и изменения висящими локально.

⛔ **The Thin Adapter Invariant (The Four Territories, AP-010 – AP-071).**
Этот репозиторий — тонкий двунаправленный адаптер (GoF Adapter) между Beyond Boundaries IDE и `@earendil-works/pi-durable`.
- Не владеть текстами промптов (извлекать динамически из `@earendil-works/pi-coding-agent`).
- Не изобретать свои UI-компоненты или кастомные FSM-движки.
- Не импортировать утекшие абстракции вне установленных портов.

⛔ **Modularity and File Line Budgets (AP-019).**
Все `.ts` файлы строго < 200 строк (soft limit 150, hard limit 250).

⛔ **Deterministic Testing (AP-028, AP-013).**
Каждый цикл сопровождается честными unit/integration тестами (`npm test`). Запрещены фейковые тесты и замаскированные ошибки.

⛔ **Dogfooding Invariant: ALL SUBTHREADS ON PI-DURABLE.**
Все вспомогательные субтреды (воркеры реализации, автономные архитектурные ревьюеры) в этом репозитории ОБЯЗАНЫ запускаться СТРОГО через `--provider pi-durable`. Запрещено съезжать на базовый провайдер `pi`. Догфудинг собственного рантайма является непреложным правилом разработки.

## Subagent Model Policy & Boundary Authority

- **Разделение зон ответственности:**
  - **Beyond Boundaries (BB)** владеет UI настроек (`app.slots.settingsSection`) и сохранением политики через namespaced KV (`subagent.policy.v1`).
  - **Pi** владеет каталогом моделей (`ModelCatalog`, `api.models`), аутентификацией/ключами и вычислением поддерживаемых уровней рассуждений (`getSupportedThinkingLevels`).
  - **Pi Durable** владеет жизненным циклом и выполнением дочерних бесед (`AgentChange`, транзакции `api.commit`, `configure`).
- **Контракт технического воркера:**
  - Минимальный технический worker envelope (`subagent-role.ts`) является разрешённым контрактом инструмента, а не собственной системной persona. Базовый системный промпт извлекается динамически из upstream.
  - Корневой координатор ведёт полный архитектурный цикл (arch loop) и публикацию; нативный воркер выполняет порученный brief в рамках роли, не становясь самостоятельным оркестратором.
  - Модель и reasoning нативного инструмента `subagent` берутся строго из сохранённой политики провайдера (`inherit` или `configured`), а не из model kwargs или жёстко заданных имён в LLM-промпте.

## Checklist for Updating the Plugin (Обязательный чеклист обновления плагина)

Обязательный протокол для любого агента, выполняющего обновление, переустановку или проверку новой версии `bb-plugin-provider-pi-durable`. Единый источник истины пользовательской инструкции закреплён в [README.md (#updating-the-plugin--existing-threads)](README.md#updating-the-plugin--existing-threads).

> **Область действия:** Данный чеклист регулирует действия агента в репозитории при выполнении задачи обновления. Он не является автоматическим фоновым хуком рантайма BB.

1. **Подготовка (Pre-Update, Drain & Handoff):**
   - До запуска установки прочитать пользовательскую инструкцию в [README.md (#updating-the-plugin--existing-threads)](README.md#updating-the-plugin--existing-threads).
   - Выяснить топологию окружения: desktop-managed локальный рантайм против attached/remote/standalone сервиса, а также определить конкретный процесс-владелец рантайма.
   - **Дренировать пользовательские работы ДО установки:** Убедиться, что завершены пользовательские задачи, независимые активные ходы и дочерние/фоновые операции. Текущий maintenance-turn самого агента-обновлятора продолжается исключительно для выполнения установки, проверок и handoff (без запуска новой пользовательской работы). Процедура установки/обновления удаляет директорию прежнего кэша, что сорвёт любые параллельно исполняющиеся инструменты.
   - **Осознавать статус собственного рантайма:** Агент, выполняющий обновление, сам исполняется на старом процессе моста. До вызова команды обновления обязательно зафиксировать согласие пользователя на прерывание сессий и сохранить handoff-квитанцию с состоянием задачи.
   - Принудительно останавливать все idle-треды заранее не требуется: достаточно дождаться завершения активной работы.

2. **Проверка активации (Installed/Activated ≠ Resident Switched):**
   - Проверить именно успешную **установку и активацию** новой версии плагина (локальная сборка сама по себе не является активной установкой; подтвердить статус активации через `bb plugin list` или API).
   - Зафиксировать фундаментальный инвариант: **активация новой версии не переключает запущенный рантайм в существующих resident-тредах** из-за платформенного удержания `processKey` в BB Core ([BB issue #4942](https://github.com/get-bb/bb/issues/4942)).
   - Запрещено объявлять об успешном переключении работающих тредов на новую версию только на основании вывода `bb plugin list` или `package.json` на диске. Чётко уведомить пользователя: плагин успешно активирован, но существующие сессии продолжают работать на прежнем процессе до перезапуска рантайма.

3. **Согласование перезапуска и безопасность (Safety Gate):**
   - Категорически запрещено автоматически закрывать приложение (Quit), убивать процессы или принудительно прерывать пользовательские сессии без явного подтверждения на каждое действие.
   - Для desktop-managed рантайма: запросить у пользователя согласованный полный выход через **Cmd+Q** (на macOS) и повторный запуск.
   - Для remote/attached/standalone хостов: согласовать перезапуск конкретного процесса/сервиса, владеющего host-daemon (или всего стека, если они связаны), с оператором хоста; отдельный перезапуск только API-сервера недостаточен.
   - Если перезапуск отложен пользователем, зафиксировать честный статус `restart: pending`.
   - Напомнить пользователю, что текущая сессия агента-обновлятора также будет завершена при выходе из приложения или перезапуске хост-демона.

4. **Верификация после перезапуска (Post-Restart Verification):**
   - При возобновлении диалога на следующем сообщении в существующем треде проверить фактическую версию и источник рантайма доступными read-only средствами (когда они доступны).
   - Если надёжная верификация поколения рантайма недоступна через открытые интерфейсы, честно зафиксировать: `active runtime generation unverified`.
   - В итоговом отчёте раздельно указывать три статуса:
     - `installed`: [версия / коммит]
     - `restart`: [completed / pending / skipped]
     - `runtime verified`: [verified / unverified]
