## 2. Результаты по Пункту 1: Конкурентный запуск `thread/start` и `turn/start`

### 2.1. Анализ контрактных условий последовательности
- Проанализированы публичные спецификации:
  - Стандарт JSON-RPC 2.0: протокол является асинхронным и полнодуплексным. Клиент имеет право отправлять запросы независимо, не дожидаясь ответа на предыдущий запрос; корреляция ответов выполняется по `id`.
  - `@get-bb/plugin-sdk` (v0.6.79) и `@bb/provider-bridge-protocol`: методы `thread/start` и `turn/start` объявлены как независимые запросы в `BRIDGE_REQUEST_METHODS`.
  - В открытой документации и типах SDK **отсутствует какое-либо документированное публичное условие**, запрещающее отправку `turn/start` до завершения `thread/start`, либо объявляющее такой вызов "Undefined Behavior".
- Обоснование из исходного отчёта `s9-product-1.4.md` о том, что данное поведение "предотвращается стандартным последовательным контрактом BB IDE", не является контрактной гарантией самого провайдера/моста:
  - Мост `dist/host.js` предоставляет публичный программный интерфейс `handleLine` (и stdio wire-протокол) для любых клиентов и интеграций.
  - Списание внутреннего сбоя синхронизации на предположение об идеальном поведении вызывающей стороны противоречит принципам надёжности и изолированного black-box тестирования.

### 2.2. Воспроизведение в изолированной временной сессии
- **Команда/сценарий:**
  В чистой временной директории (`BB_PI_BRIDGE_SESSION_DIR`) после `initialize` одновременно отправлены:
  1. `{"jsonrpc":"2.0","id":2,"method":"thread/start","params":{"threadId":"thr_concur_1","providerThreadId":"pi_durable_concur_1",...}}`
  2. `{"jsonrpc":"2.0","id":3,"method":"turn/start","params":{"threadId":"thr_concur_1","providerThreadId":"pi_durable_concur_1","clientRequestId":"req_concur_1","input":[{"type":"text","text":"Say hello"}],...}}`
- **Фактический результат (Evidence):**
  1. Хост-мост начал процедуру запуска первого процесса runner для запроса `thread/start`.
  2. Запрос `turn/start`, поступивший до завершения инициализации первого runner, не встал в очередь ожидания и не был отклонён с понятной ошибкой: хост-мост запустил **второй процесс runner на той же сессионной директории** `pi_durable_concur_1`.
  3. Второй runner попытался перехватить блокировку директории, в результате чего первый runner аварийно завершился до выхода на рабочий режим (`code 0, signal null`), выдав в stderr:
     ```text
     [SessionStorage] unlock warning for .../pi_durable_concur_1: Lock is not acquired/owned by you
     ```
  4. Запрос `thread/start` (`id: 2`) вернул необработанную ошибку JSON-RPC:
     ```json
     {"jsonrpc":"2.0","id":2,"error":{"code":-32000,"message":"Runner exited before becoming ready (code 0, signal null)"}}
     ```
  5. Последующее выполнение хода перешло в состояние прерывания (`turn.boundary (status: "interrupted", error: { message: "aborted" })`).
- **Публичный Teardown:**
  Вызов `teardown(0)` корректно завершил активные дочерние процессы, в системе не осталось зависших процессов `node/runner`.

### 2.3. Классификация дефекта
- **Severity: P1 (Critical Journey Failure / Unhandled Runtime Crash on Concurrent Dispatch)**
- **Finding:**
  - **Title:** [P1] Отсутствие сериализации `turn/start` во время незавершённого `thread/start` приводит к гонке процессов, вытеснению блокировки сессии и падению `thread/start` с ошибкой `-32000`.
  - **Journey:** Error Recovery & Edge Cases.
  - **Action:** Отправка `turn/start` до получения ответа на `thread/start` в рамках одного треда и одной сессионной директории.
  - **Expectation:** Хост-мост должен либо сериализовать запросы к одному треду (ставить `turn/start` в очередь до подтверждения готовности runner), либо возвращать понятную ошибку занятости/неготовности сессии.
  - **Reality:** Запускается второй параллельный процесс runner на том же каталоге, первый runner вытесняется и падает, клиент получает необработанную ошибку `-32000 Runner exited before becoming ready (code 0, signal null)`.
  - **Rule:** SKILL.md (P1: Command crashes with an unhandled runtime error), AP-021 (Failure Modes & Recovery).
  - **Fix decision:** `fix-now`.

## 3. Результаты по Пункту 2: Native child/mirror reconnect

### 3.1. Анализ покрытия в исходном отчёте `s9-product-1.4.md`
- В отчёте `s9-product-1.4.md` (Journey 3, шаг 6) проверялся **исключительно отрицательный кейс**:
  - Вызов `thread/resume` с `providerThreadId: "pi_durable_parent_1:2"` при отсутствии второй беседы в БД.
  - Результат: ошибка `Error: Conversation 2 does not exist`.
- Положительный сценарий переподключения к существующей дочерней беседе subagent (`native child/mirror reconnect`) в исходном отчёте **не выполнялся**.

### 3.2. Верификация через публичный интерфейс
- **Сценарий верификации:**
  1. Через публичный метод `thread/start` создана родительская сессия (`thr_parent_1`, `pi_durable_parent_1`), инициализировавшая валидное хранилище `session.sqlite` с корневой беседой `id: 1`.
  2. В сессионном хранилище SQLite зафиксирована дочерняя беседа (`id: 2`, `owner_conversation_id: 1`, record: `{"id":2,"parentConversationId":1}`).
  3. Через публичный интерфейс отправлен запрос `thread/resume` с составным идентификатором:
     ```json
     {
       "jsonrpc": "2.0",
       "id": 3,
       "method": "thread/resume",
       "params": {
         "threadId": "thr_child_1",
         "providerThreadId": "pi_durable_parent_1:2",
         "cwd": "/path/to/cwd",
         "instructionMode": "append",
         "options": { ... }
       }
     }
     ```
- **Фактический результат (Evidence):**
  - Запрос `thread/resume` успешно разрешился за **102 мс** с кодом результата:
    ```json
    {"jsonrpc":"2.0","id":3,"result":{"providerThreadId":"pi_durable_parent_1:2","sessionRestorable":true}}
    ```
  - В поток событий отправлены корректные дельты:
    - `thread/identity`: `{"threadId":"thr_child_1","providerThreadId":"pi_durable_parent_1:2","sessionRestorable":true}`
    - `thread/delta`: `{"kind":"session.reset"}`
  - Дочерняя беседа успешно распознана и привязана к треду Beyond Boundaries без конфликтов.
  - Штатный `teardown(0)` корректно закрыл runner без утечек файловых дескрипторов и lock-файлов.

### 3.3. Граница покрытия
- **Что доказано:** Публичная поверхность моста (`dist/host.js`) и runner полностью поддерживают положительный reconnect к дочерней беседе subagent по составному идентификатору `<parentSessionId>:<childConversationId>`. Протокол маршрутизации дочерних бесед функционирует корректно.
- **Граница покрытия:** Создание дочерней беседы с нуля в рамках автономного хода (через инструмент `subagent`) требует полноценного диалогового цикла с внешней LLM и расхода квот API, что выходит за рамки изолированного smoke-теста локального протокола. Проверка проведена на реальном протоколе и реальном SQLite-рантайме с предварительным созданием дочерней беседы.
