## 3. Валидация параметров инструментов и `@earendil-works/pi-schema`

### 3.1. Архитектурный переход: Отказ от TypeBox в ядре
В Pi 1.5.0 пакет `@sinclair/typebox` **полностью исключён из зависимостей** пакетов `@earendil-works/pi-durable`, `@earendil-works/chord` и `@earendil-works/pi-codemode`. Валидация аргументов инструментов и схем структурированного вывода переведена на новый zero-dependency пакет `@earendil-works/pi-schema`.

В `@earendil-works/pi-ai` функции `Type`, `Static` и `TSchema` сохранены исключительно как compat-слой для внешних плагинов, но внутренний валидатор `validateToolArguments` в `packages/ai/src/utils/validation.ts` переведён на `pi-schema`.

#### Ключевые различия билдеров pi-schema и TypeBox:
| Параметр / Билдер | TypeBox (`Type.*`) | pi-schema (`@earendil-works/pi-schema`) | Поведение и влияние на код |
|---|---|---|---|
| Объект | `Type.Object(props)` | `obj(props, { open?: boolean })` | **КРИТИЧНО:** `obj()` в pi-schema **ЗАКРЫТ** по умолчанию (`additionalProperties: false`). Чтобы разрешить произвольные поля, требуется явный флаг `{ open: true }`. |
| Число / Целое | `Type.Number()`, `Type.Integer()` | `num()`, `int()` | Генерирует `{ type: "number" }` / `{ type: "integer" }`. |
| Строка | `Type.String()` | `str()` | Поддерживает `minLength`, `maxLength`, `pattern`, `format`. |
| Булево | `Type.Boolean()` | `bool()` | `{ type: "boolean" }`. |
| Перечисление | `Type.Enum(...)` | `oneOf([...])` | Принимает массив строковых литералов, формирует `{ enum: [...] }`. |
| Литерал | `Type.Literal(v)` | `lit(v)` | Формирует `{ const: v }` без избыточного `type`. |
| Опциональное поле | `Type.Optional(T)` | `opt(T)` | Применяется только как свойство внутри `obj(...)`. |
| Массив | `Type.Array(T)` | `arr(T, { minItems, maxItems })` | `{ type: "array", items: T }`. |
| Записи (Словарь) | `Type.Record(K, V)` | `map(V)` | `{ type: "object", additionalProperties: V }`. |
| Объединение | `Type.Union([...])` | `union([...])` | `{ anyOf: [...] }`. |
| TypeBox типы вне JSON Schema | `Type.Refine()`, `Type.BigInt()`, `Type.Undefined()`, кодеки | **НЕ ПОДДЕРЖИВАЮТСЯ** | `Refine` молча игнорируется при валидации аргументов; `BigInt` реджектится как неподдерживаемый тип JSON. |

### 3.2. Унифицированная 3-фазная коэрция типов (Coercion Parity)
В Pi 1.4.0 коэрция аргументов была разорвана:
- Схемы TypeBox проходили через `Value.Convert()` (конвертация чисел, булевых, оборачивание в массивы).
- Обычные JSON Schema (включая все MCP инструменты) проходили через примитивный `coerceSerializedArguments` в `pi-ai`, где отсутствовали правила оборачивания в массивы и обработка `null`. Из-за этого вызовы MCP инструментов моделями часто падали с ошибками типов.

В Pi 1.5.0 компилятор `compile(schema, { formats, coerce: true, unresolvedRefs: "reject" })` применяет **строгий 3-проходный алгоритм коэрции для ВСЕХ схем** (и нативных, и MCP):
1. **Pass 1 — Опциональные null:** Если свойство объявлено как опциональное и его схема не разрешает `null`, переданное значение `null` удаляется, как будто поле не было передано (`undefined`).
2. **Pass 2 — Семантическая конвертация по ключевым словам JSON Schema (на базе правил TypeBox 1.3.27 `Value.Convert`):**
   - `number`: строки с числами (`"42"` → `42`, `" 12 "` → `12`, `"0x10"` → `16`, `""` → `0`), строки `"true"`/`"false"`, булевы значения `true` → `1` / `false` → `0`, `null` → `0`.
   - `integer`: аналогично числу с последующим усечением до целого (`"3.7"` → `3`, `3.7` → `3`).
   - `boolean`: строки `"true"`/`"false"` (регистронезависимо), `"1"`/`"0"`, числа `1`/`0`, `null` → `false`.
   - `string`: числа и булевы значения переводятся в строку (`42` → `"42"`), `null` → `"null"` (для обязательной строки).
   - `array`: **скалярное значение автоматически оборачивается в одноэлементный массив** (например, `7` → `[7]`, `"file.txt"` → `["file.txt"]`), после чего элементы коэрцируются. Кортежи (`prefixItems`) никогда не оборачиваются.
   - `const`/`enum`: преобразует значение к соответствующему члену перечисления.
3. **Pass 3 — Примитивная коэрция типов Ajv (для объединенных типов `type: ["integer", "null"]`):**
   - Дополнительная доводка неразрешенных типов. При конфликте правил Pass 2 имеет приоритет.

### 3.3. Изменение формата ошибок валидации
Формат сообщений об ошибках кардинально изменился.
- **В Pi 1.4.0 (TypeBox):**  
  Сообщения содержали фразы вроде `must have required properties path`, `must be number`.
- **В Pi 1.5.0 (pi-schema):**  
  Ошибки форматируются по стандарту JSON Pointer, преобразованному в точечную нотацию:
  ```text
  Validation failed for tool "<tool_name>":
    - <path>: <message>

  Received arguments:
  {
    ...
  }
  ```
  Примеры конкретных сообщений:
  - Отсутствующее обязательное свойство: `- path: missing` (вместо `must have required properties path`).
  - Несовпадение типов: `- limit: expected number, got string`.
  - Лишнее свойство в закрытом объекте: `- extra_field: unknown field`.
  - Нарушение минимума: `- offset: expected >= 1`.
  - Элемент перечисления: `- choice: expected one of ["a", "b"]`.

### 3.4. Влияние на `tool-adapter.ts` и `extension-mount.ts`
В нашей текущей кодовой базе (`bb-plugin-provider-pi-durable/src/runner/tool-adapter.ts`):
1. **Сигнатура `defineTool`:**
   В 1.4.0: `defineTool<TParameters extends TSchema>(...)`.  
   В 1.5.0: `defineTool<TParameters extends object>(...)`.  
   Больше не требуется приведение `toolDef.parameters as import("typebox").TSchema` и `toolDef.outputSchema as import("typebox").TSchema`. Параметром может быть любой объект JSON Schema.
2. **Валидация `structuredOutputSchema`:**
   В `packages/durable/src/harness/tool.ts` валидация структурированного вывода теперь кэшируется через `WeakMap<object, Validator>`:
   ```ts
   validator = compile(schema, { formats, unresolvedRefs: "reject" });
   ```
   Если расширение возвращает `structuredOutput`, не соответствующий схеме, Durable формирует ошибку:
   `Tool ${tool.name} returned structuredOutput that does not match its schema: ${path}: ${first?.message ?? "invalid"}`.
3. **Безопасность `$ref` для MCP инструментов:**
   Опция `unresolvedRefs: "reject"` компилирует висячие `$ref` как локальный `false`, предотвращая падение всего рантайма при битых ссылках в схемах сторонних MCP-серверов.

## 4. Архитектура Durable Core (`@earendil-works/pi-durable`)

### 4.1. Механизм Group Commit (Спецификация §4, docs/group-commit.md)
В Pi 1.4.0 сессия имела единую строго последовательную линию мутаций (`SessionImpl.#tail`). Каждый коммит выполнял коллбэк, вызывал `Storage.commit()` и ждал завершения синхронной дисковой операции SQLite WAL, удерживая всю сессию. При наличии нескольких параллельных субагентов или вызовов инструментов пропускная способность упиралась в задержку диска (26.8 запусков/сек при задержке 4 мс).

В Pi 1.5.0 внедрён **Group Commit**:
1. **Параллельное исполнение коллбэков на линии:** Коллбэк мутации может выполняться, пока предыдущий коммит всё ещё записывается на диск бэкендом хранения.
2. **Keyed Gates (Ворота по ключам):** Коллбэк выполняется на полной скорости до тех пор, пока не коснется (на чтение или запись) ключа, который был изменен еще не опубликованным коммитом.
   - Ключи отслеживания: `task:<id>`, `owned:<node>`, `roots`, `intent`, `conv:<id>`, `entry:<id>`, `entry-append:<conv>`, `sub:<id>`, `doc:<address>`, `docscope:<scope>`.
   - При попадании на горячий ключ операция ожидает открытия гейта конкретного коммита.
3. **Пакетная запись (Storage Batches):** Коммиты, накопившиеся в очереди, пока предыдущий I/O был в полете, объединяются в единый вызов `Storage.commit(batches, receive, context)`.
4. **Гарантия строгой упорядоченности:** Результаты отдаются строго в порядке линии. Опубликованные коммиты видны наблюдателям без пропусков.

### 4.2. Изменения в контракте `Storage` и SQLite
Метод `Storage.commit` претерпел фундаментальный breaking change:
```ts
// До (v1.4.0):
commit(writes: readonly StorageWrite[], adopt: (seq: Seq) => void, context: Context): Promise<Seq>;

// После (v1.5.0):
commit(
    batches: readonly (readonly StorageWrite[])[],
    receive: (index: number, seq: Seq) => void,
    context: Context,
): Promise<{ readonly stored: number; readonly refused?: unknown }>;
```
- **SQLite бэкенд (`SqliteStorage`):**
  Выполняет ВСЕ пачки коммитов в **одной транзакции SQLite**:
  `BEGIN TRANSACTION` → для каждого батча: `checkBatch()` → `applyBatch()` → `COMMIT`.
  Если внутренние проверки Durable бракуют батч $k$, транзакция коммитит батчи $0..k-1$, вызывается `receive(index, seq)` для сохраненных батчей, а вызов возвращает `{ stored: k, refused: error }`.
- **`SqliteExecutor.runCounted`:**
  В интерфейс `SqliteExecutor` (экспортируемый из Chord) добавлен метод `runCounted(sql, ...params)`, возвращающий количество фактически измененных строк.
- **Схема SQLite `session.sqlite`:**
  **Схема БД НЕ ИЗМЕНИЛАСЬ (версия остаётся 2)**. Структура таблиц `durable_records`, `durable_documents`, `durable_entries`, `durable_tasks`, `durable_metadata` идентична 1.4.0. Новых SQL-миграций между 1.4.0 и 1.5.0 нет. Существующие файлы `session.sqlite` открываются прозрачно.

### 4.3. Версионирование встроенных документов
Хотя схема таблиц SQLite осталась прежней, внутренние схемы документов получили мажорные обновления:
1. **`pi.live` (версия 3):**
   - Добавлено обязательное поле `run.turns` (счетчик раундов инструментов в текущем запуске).
   - В `compactionFailure` и `compactionStatus` поле `reason` переименовано в `trigger`.
   - Добавлено поле `runFailure` (`RunFailureReason`: `model_error`, `no_model`, `aborted`, `reset`, `faulted`, `orphaned`, `interrupted`, `restart_limit`, `nothing_to_answer`, `turn_limit`).
2. **`pi.tool` задача (версия 3):**
   - Добавлен флаг `unoffered: true` для вызовов инструментов, которые не предлагались модели в промпте (завершаются статусом `tool_unavailable` через стандартный цикл задачи).
3. **`pi.generation` задача (версия 2):**
   - Обновлен протокол последовательных раундов генерации.

### 4.4. Кэши памяти и отложенные коммиты (Deferred Commits)
- **Zero Storage Reads в ходе рана:** `HarnessImpl` держит в памяти LRU-кэши последних прочитанных задач, бесед, сабмишенов и документов живых задач.
- **Замороженные объекты (`Object.freeze`):** Все объекты, возвращаемые через `tx.task()`, `tx.conversation()`, `getTask()`, `runtime.entry()`, являются замороженными ссылками на кэш памяти. **Любая попытка прямой мутации полей (`entry.data = ...`) выбросит `TypeError`!**
- **Отложенные коммиты прогресса (`settings.progress.persistWithinMs`, по умолчанию 1000 мс):** Промежуточный стриминг текста ответа и статусы работающих слотов инструментов (`running`) больше не вызывают синхронных транзакций SQLite. Они фиксируются в памяти и сбрасываются на диск пачкой либо раз в секунду, либо по завершении раунда. Это снижает количество транзакций SQLite в 5.7–27 раз.

### 4.5. `submit-in-commit` и атомарная подача сообщений
Появилась перегрузка `Conversation.submit(tx, draft)`:
```ts
await root.commit(async (tx) => {
    // Проверяем локальное состояние хоста и подаем сообщение в одной транзакции:
    const id = await root.submit(tx, {
        type: "input",
        content: "...",
        whenBusy: "steer",
        whenIdle: "reject",
        requestId: "...",
    });
});
```
Опция `whenIdle: "reject"` выбрасывает `ConversationIdle`, если агент не занят выполнением, предотвращая гонки между проверкой статуса и подачей сообщения.

### 5.2. Сокращение Union-типов в секции `<codemode>` (`#11501`)
В Pi 1.4.0 при наличии инструментов со сложными union-типами вывода (например, `process` с 7 вариантами) в системный промпт на каждом шаге инжектировалось до 8 000 символов определений типов TypeScript, что приводило к деградации контекста и финансовым перерасходам.

В Pi 1.5.0 внедрен алгоритм сжатия `describeOutput`:
1. **Объединения объектов (`anyOf`/`oneOf`):** Функция `describeUnionFields` сворачивает типы в краткий список полей:
   ```ts
   `{ action: "start", process } | { action: "list", processes, truncated? }`
   ```
2. **Дискриминаторы (`const`):** Значения константных полей сохраняются в сигнатуре, позволяя модели видеть доступные действия.
3. **Многострочные сложные типы:** Если тип вывода занимает несколько строк и не является простым объединением объектов, он заменяется указателем:
   ```text
   a value; `await describeTool("tool_name")` shows its type
   ```
4. **Однострочные типы (`number`, `string`):** Остаются компактными инлайн-типами. Полное TypeScript-описание возвращается по запросу через `await describeTool(name)`.

### 5.3. Обновление поискового движка `searchTools()` (BM25 + Unicode/CJK)
В `packages/durable/src/search.ts` полностью переработан токенизатор и ранжирование:
1. **Поддержка CJK и не-ASCII (`Intl.Segmenter`):**
   - Раньше токенизатор отсекал любые символы, кроме ASCII букв и цифр (`/[^a-z0-9]+/`). Запросы на китайском, японском, тайском языках или на кириллице не находили ничего.
   - Теперь токенизатор нормализует строку в Unicode NFC и использует `new Intl.Segmenter(undefined, { granularity: "word" })`. Слова без пробелов (например, `搜索记录`) корректно разбиваются на токены.
   - Каноническая эквивалентность: `café` и `cafe\u0301` дают одинаковые токены.
2. **Алгоритм ранжирования Okapi BM25:**
   - **Точное совпадение имени:** Если запрос совпадает с полным именем инструмента или суффиксом после `__` (например, `thread_read` для `mcp__app__thread_read`), инструмент получает наивысший приоритет (`exact: true`) и выводится первым независимо от BM25-скора.
   - **Вес совпадения в имени (`NAME_WEIGHT = 3`):** Совпадение термина в имени инструмента весит втрое больше, чем в описании.
   - **Покрытие терминов (`covered`):** Инструмент, содержащий больше слов из запроса, всегда ранжируется выше инструмента с одним словом, даже если у последнего выше частота слова.
   - **Поиск по инструкциям неймспейса (`NAMESPACE_WEIGHT = 0.5`):** Описания серверов MCP участвуют в поиске, позволяя находить инструменты по назначению сервера.

## 6. Субагенты, фоновые задачи и наблюдатели

### 6.1. Полное удаление `watchEvents()` (P0 Breaking Change)
В Pi 1.5.0 **полностью удалена функция `watchEvents()`** и все связанные типы:
- `AgentEvent`, `AgentEventStream`, `SnapshotEvent`, `MessageChange`, `ToolEventCall`.
- Спецификация §9.4 аннулирована.

**Архитектурное обоснование upstream:**  
Рендереры и UI-адаптеры больше не должны вручную собирать состояние из потока гранулярных событий. Всё состояние концентрируется в `ConversationView` и документе `pi.live`:
- Стриминг ответа находится в `pi.live.generation.message`.
- Прогресс инструментов — в слотах `pi.live.tools` и `pi.live.nestedTools`.
- Причина завершения — в `pi.live.runFailure`.
- Для отслеживания изменений используется `Conversation.watch()` (возвращает `WatchHandle<ConversationView>`), а дельты передаются через стандартные операции патча (`call.ops`).

### 6.2. Новый оконный `ConversationTranscript`
`ConversationView.entries` больше не содержит полный транскрипт за всю историю беседы. Это скользящее окно (по умолчанию от 50 до 100 последних записей).
Для поддержания полного списка сообщений и бесшовной загрузки истории внедрён вспомогательный класс `ConversationTranscript`:
```ts
const transcript = new ConversationTranscript((query, limit, ctx) => conversation.entries(query, limit, undefined, ctx));
const watch = await conversation.watch(context);

// Слияние окна с локальной историей:
render(transcript.merge(watch.value));

watch.start(async (call) => {
    if (call.kind === "value") {
        render(transcript.merge(call.value));
    }
});

// Догрузка истории при скролле вверх или наличии пропусков (gaps):
await transcript.loadEarlier(context);
await transcript.fillGap(gap, context);

// Восстановление после дисконнекта с точным продолжением:
const resumedWatch = await conversation.watch(context, transcript.resume);
```

### 6.3. Контракт `WatchHandle`, `WatchCall` и `WatchEnd`
Все вотчеры переведены на сигнатуры Chord v2:
1. **Коллбэк `start()`:**
   - 1.4.0: `watch.start(async ({ value, ops }) => ...)`
   - 1.5.0: `watch.start(async (call, context) => ...)`  
     где `call` имеет тип `WatchCall<T>`:
     - `{ kind: "value", value: T, ops: readonly Op[], retired: boolean }`
     - `{ kind: "failed", error: unknown }` (временная ошибка источника, вотчер не закрывается).
2. **Завершение `closed` и `stop()`:**
   - 1.4.0: возвращали `{ reason: "stopped" | "cancelled" | "session_closed" }`.
   - 1.5.0: возвращают `WatchEnd`:
     - `{ kind: "stopped" | "aborted" | "ended" }`
     - `{ kind: "listener_error", error: Error }`
     - `{ kind: "failed", error: unknown }`
3. **Отслеживание документов (`DocumentWatch<T>`):**
   Удаление документа больше не завершает вотчер статусом `retired`. Вотчер продолжает жить, получая кадр с флагом `retired: true`. При повторном создании документа по тому же адресу данные приходят как `[["r", value]]`.

### 6.4. Задачи: Лимит перезапусков и отказ от парковки (`task_parked`)
- В 1.4.0 задача, упавшая 5 раз подряд, «парковалась» (`task_parked`), требуя ручного вызова `Harness.retryTask()`.
- В 1.5.0 **парковка и `Harness.retryTask()` удалены**:
  - Задача, упавшая `settings.restartLimit` раз (по умолчанию 5), **завершается окончательно с ошибкой**:
    - Инструмент возвращает диагностику `restart_limit`.
    - Генерация завершает ран статусом `runFailure: { reason: "restart_limit" }`.
    - Сабмишены переводятся в статус `unanswered` с причиной `restart_limit`.
  - Отчёт регистрируется через `onReport` как `task_interrupted` (для встроенных задач) или `task_faulted` (для расширений).
- Статус задачи в `TaskInspection.state`: значение `ready` переименовано в `pending` (`{ kind: "pending" }`).

## 9. Заключение

Релиз Pi 1.5.0 представляет собой качественный скачок в производительности и архитектурной чистоте платформы:
- **Group Commit** устраняет бутылочное горлышко дискового I/O в SQLite WAL, поднимая пропускную способность параллельных сессий на порядок (до 10x–16x).
- **`@earendil-works/pi-schema`** обеспечивает абсолютный паритет коэрции типов между нативными и MCP инструментами, защищая вызовы от некорректных типов моделей.
- **Удаление `watchEvents`** в пользу проекций `ConversationView` и `ConversationTranscript` устраняет рассинхронизацию между транзакционным дисковым хранилищем и UI-рендерером.

Разработанный 5-этапный план миграции минимизирует риски, обеспечивает пошаговую TDD-верификацию и сохраняет 100% обратную совместимость данных в существующих базах данных `session.sqlite`.
