## 5. Old sessions — expected behavior and proof required

Expected user journey, not an untested guarantee:

1. Thread remains the same BB thread and provider identity; previous messages/checkpoints/bindings stay addressable.
2. A new 1.4 runner opens the same native session, migrates it once, and reads its existing transcript/documents.
3. Old terminal entries remain; pending work follows upstream recovery; unsafe interrupted tools are not promised transparent re-execution.
4. The next user input is admitted exactly once by the new runner, not silently handled by an old process.
5. Remaining idle sessions are migrated only when actually reopened; no all-session eager migration.

Proof must include root-only, child-first reconnect, pending generation/tool, custom courier/report/hold, native bindings, policy ACK if present, edited/forked checkpoint, and old database rollback rehearsal on a COPY.

A plugin source switch does not itself change the SQLite schema. Opening a session with 1.4 does. Schema v2 cannot be reopened by 1.3. A pre-upgrade snapshot can restore the old state, not magically preserve later 1.4 writes; preserve failed/new state separately and obtain approval before any destructive restore.

## 6. Gate G-LOCAL — global blast radius and source-change blocker

The user states all their threads use this plugin. A local install of the SAME plugin/provider ID replaces the provider for this BB installation; it is not per-thread isolation.

Verified BB behavior:

- `assertInstallRegistrationAvailable` refuses Git -> path replacement and asks to remove first.
- `remove()` disposes the plugin, forgets provider registration and deletes settings, secrets and schedules. Do not assume plugin KV/metadata survives; verify complete state recovery too.
- `bb plugin dev` watches/builds/reloads. It is not a safe source-selection shortcut and should not watch the live development checkout in production.
- The native DB directory lies outside the plugin cache, but that alone does NOT prove end-to-end restoration.

Primary BB sources, from `server/dist/start-server.js.map` originals: `plugin-registration.ts:296–321`; `plugin-service.ts:1267–1281,1721–1767`.

**No production source replacement command is supplied as an automatic step.** First prove a supported source/state preservation route in a disposable environment. If the running BB exposes no non-destructive replacement, stop and present a recoverability card (settings/secrets/KV/schedules/native DBs/BB bindings, recovery point and post-snapshot writes), then wait for explicit per-instance approval. Do not patch BB private SQL to bypass the guard.

Before cutover: all relevant root/child foreground AND background work must be drained or explicitly handled; do not use the provider's ordinary idle status as proof that background work is absent. Execute cutover from an operator terminal/control path not running on the provider being replaced. Do not terminate this orchestrator to prove its own continuation.

## 7. Backup and isolation contract

- Inventory canonical session paths and owner PID liveness without opening a Harness. Metadata only; no transcript/token dumps.
- Produce transactionally consistent SQLite backups via SQLite backup API / supported snapshot while handling WAL. Plain `cp session.sqlite` while a writer is active is insufficient.
- Snapshot BB registration/settings/bindings and protected plugin state using a tested supported recovery route. No plaintext secret export into repo, thread logs or new env files.
- Backup dir protected (0700), backup files protected (0600), checksums + `PRAGMA quick_check` and restore-open tests recorded without personal content.
- Canaries use new COPY paths, not original paths, and do not copy live owner/lock metadata. Never register duplicate provider IDs in the production installation to simulate isolation.
- Keep the current tagged plugin artifact + install intent available for recovery. Do not assume uninstall preserves its cache.
- No production DB opens with 1.4 before backup/restore proof and G-LOCAL approval.

## 8. Graph acceptance contract

- Actual task lifecycle and phases only: pending/running/waiting/sleeping/completing/terminal; blocked reason is metadata, not an invented TaskState.
- Preserve all terminal outcomes: completed/failed/aborted/faulted/orphaned.
- Distinguish completed task + tool result `isError` from failed task.
- Owner edges and wait edges are different; conversation history parent is not execution owner.
- Native child ownership remains stable after an anchor becomes terminal.
- Missing/deleted live node means receipt must be reconciled, not automatic success.
- Expose background/abort request as badges, not fake terminal states.
- Connection/runner readiness is separate from task state. Old snapshot cannot keep pretending to be live.
- No progress percentages, inferred human phases, model-generated graph JSON, fake phase timing or new scheduler.
- Active tree in context segment; stable selection/scroll; optional time bars with labelled lifetime; true tool execution duration separate; one bounded inspector; keyboard/reduced motion/theme support.
- v1 scope: live graph + explicitly bounded recent authoritative results; not a complete persisted phase timeline or semantic project plan. Message embeds are deferred, not an implicit extra feature.
